# Operative Procedure Website

Start from the working Pterional Craniotomy site in `assets/source/`. Treat its page as the exact interface and behavior template for every requested operation or operation family. Preserve the CSS, layout, shading code and parameters, animation controls, flap deformation contract, camera controls, mobile behavior, labels, layers and comparison tools. Adapt the clinical content, region-specific structures, instruments, markings, step states and hinge/geometry placement from evidence. Reuse matching pterional anatomy only where applicable. Add only the variants the user requests. The bundled reference is based on the Pterional Craniotomy revision pinned in `assets/source/reference-revision.json`. The same file records the camera implementation from Pterional PR #1 and the bundled file hashes. Run `node scripts/check_reference_controls.cjs` after changing the reference. Reuse that implementation; do not approximate the features with a replacement renderer.

The bundled reference includes regional cranial meshes. If the requested region needs anatomy outside that subset, resolve the atlas dependency using [the atlas setup instructions](assets/source/atlas-tools/anatomy.md). Check local assets first, then run the pinned setup helper as part of the workflow when needed. Ask the user for anatomy files only if neither route supplies the needed anatomy.

For an existing guide, edit the affected source in place. Reuse its evidence and geometry; restart research only for a new procedure or unsupported clinical change. Do not regenerate unchanged anatomy for a text, style or input-control edit.

## Work proportionately

For an existing guide, change the affected frontend, content, or procedure state in place; reuse evidence, geometry, and compressed anatomy assets. Research is required for a new procedure or an unsupported clinical change. Run focused checks on changed controls, states, sources, laterality, and geometry as applicable. Do not regenerate unchanged assets, build every export, or repeat unaffected checks. A new guide or substantial anatomical change warrants the broader review described below; a routine frontend edit does not.

## 1. Research first, then request PDFs

Read [research and source handling](references/research.md). Materialize a new project shell with the helper described in section 3 before saving intake there; this shell preparation does not establish a new procedure. Resume an existing materialized project on later PDF uploads instead of materializing into it again. Identify the named procedure, anatomical region, intended extent and any variants the user explicitly wants. A single procedure is the default. Do not invent top-level option groups. For a requested procedure family, derive the option axes from the user's scope and evidence; clarify only consequential ambiguity.

Find primary operative technique and microsurgical anatomy papers, verify their bibliographic identities and full-text access, and request the specific missing PDFs in one concise prioritized list. Give titles, authors/year, DOI or article link, and what each will resolve. Use accessible full text directly and recognize PDFs already supplied. Do not ask the user to upload an obtainable open-access PDF again. Ask for additional figure pages only when an uploaded file actually lacks them.

**Pause evidence-dependent final step writing and geometric reconstruction while required PDFs are missing.** A research shortlist and the reusable shell can be prepared during this phase. Keep a saved intake/source-status file so the next upload resumes the same project. Do not substitute abstracts, guessed dimensions or a different technique for missing operative evidence. Once the needed PDFs arrive, continue autonomously through the build and review; another approval round is unnecessary.

## 2. Inspect the papers and plan the procedure

Read the complete supplied technique PDFs and visually inspect the pages containing operative photographs, diagrams, instrument positions and tissue planes. Use an available PDF workflow. Use source diagrams to inform anatomy and geometry. Map original source figures to the corresponding guide steps and keep schematic markings in the 3D model.

Complete the paper-by-paper extraction and disposition audit in the research reference, then make a source-to-step evidence map and procedure plan before modeling. Carry forward every relevant supported detail into the model, steps, views, or supporting source notes. Keep page/figure anchors, evidence limits, source applicability and disagreements in working data. Full-text access is not proof that a particular step, variant or measurement is supported.

Use **one meaningful operative action or anatomical transition per step**, at the granularity of the reference's 27-step positioning-to-closure sequence. Read [the interface and content contract](references/website-contract.md). Match density and importance, not a fixed count: a simpler procedure can need fewer steps and a more complex one more. Do not compress an entire exposure into one card or pad it with trivial actions. Each card has an action title and 2–4 short sentences explaining what happens, the relevant anatomy, and why. Keep study names, citations and user-specific provenance out of Guide prose.

## 3. Adapt the working website

Read [implementation and anatomy](references/implementation.md). If the project was not already materialized during intake, use `scripts/materialize_site.py --skill-dir <this-skill> --output <new-project-path>` to copy and unpack the retained source into an editable project. Work on the copy. Preserve the reference CSS and controls instead of scaffolding a visually different site. The helper also retains the working baseline for comparison. Never edit the skill's reference assets during use.

Review every case-specific sequence, indication, paper, source text, label anchor, atlas selection, anatomical transform, mask, instrument placement and marking. Replace each item that does not fit the requested scope. The copied runtime is a pterional implementation; its coordinates and clinical logic are **reference code**, not a universal surgery engine. Follow the adaptation map and implement the new procedure's geometry and state machine explicitly. Trace the adapted runtime and remove reference helpers, shader branches and styles that the chosen procedure cannot exercise. Verify the affected controls and rendered views against the working baseline.

Maintain a page-parity inventory as the procedure is adapted: header, viewport/panel arrangement, tissue palettes and shader uniforms, layered visibility, progressive exposure and reverse closure, flap pose/scrubber/replay, markings and instruments, camera/patient-pose controls, labeling/picking, published source figures, responsive controls and accessibility. For each item, retain the working source implementation or map it to the operation's corresponding anatomy/action; document any anatomically inapplicable item rather than silently deleting it. Keep the renderer and the same visual grammar even for a region such as the cervical spine. For a family of operations, generate only evidence-supported requested choices and confirm that changing each choice changes the sequence, geometry, instruments, source mapping and relevant views. A name or step-text swap over pterional meshes is not a completed adaptation.

For a single procedure, remove the top variant selectors and omit model counts; retain the title, side/context and normal model controls. For a requested family, show clearly labeled top selectors and generate every supported requested combination. Do not carry over the example's 12-model count or its clinoidectomy / temporalis / Sylvian choices. Represent evidence-limited combinations honestly in Papers/Indications; do not imply that selectable combinations have been clinically validated.

Keep the camera and gesture implementation from Pterional PR #1 as bundled in the reference. Use one fixed model-space orbit pivot derived from stable native anatomy bounds, using the cranial vault for skull procedures and the full displayed vertebral span for spine procedures. Route Anterior, Left, Right, Posterior, Top, Surgeon’s View, Recommended View, Reset View and Focus Change through that pivot and clear pan when selecting any of them. Use the same trackball for every view. Keep the operation-specific directions for Surgeon’s View, and use the preset’s default magnification. Set the first step’s camera to a full anatomy overview. Make Reset View and Home restore that opening angle, distance and magnification at any step without changing procedure state. Give directional presets the same overview distance and magnification. Keep step close-ups available through Recommended View and Focus Change. Preserve the complete camera during ordinary step navigation and switching to 2D Figures. See [implementation](references/implementation.md) for the input and projection details.

Read [geometry and clearance](references/geometry-and-clearance.md). Verify native transforms, mirrored winding, mesh coverage, cut surfaces, and fit against the relevant native landmarks. Audit full instrument and hardware trajectories as well as tissue motion. Keep moving participants visible and hold incidental stationary exclusions for the full step. Use the bundled geometry checks to verify representative static and sampled motion positions. Fix unwanted crossings in the modeled anatomy or operative path before treating display exclusions as sufficient.

Preserve Surgical/Atlas palettes, per-tissue shading and baked ambient occlusion; layered scalp, galea and pericranium where applicable; conforming dura/fascia/fat, veins and arachnoid; progressive incisions and layered closure; and the existing CPU/GPU curl/peel deformation for flap motion. Keep surface-following markings synchronized with the actual procedural state. Read [the PR feature and reuse map](references/lifelike-reference.md) before adapting these systems. These are source-based illustrations, not patient-specific geometry or soft-tissue physics.

## 4. Verify with an independent reviewer

Read [verification and review](references/verification.md). Run syntax, data, state/branch, laterality, geometry and interaction checks appropriate to the new case. Inspect the actual website in a permitted browser when available; never bypass a browser-access denial or call a software projection a browser screenshot.

For a new guide or substantial anatomy or sequence change, use a separate review agent when available and appropriate to inspect the changed anatomy, applicable sources, variants and sides. Routine frontend edits need only focused checks. Have it report concrete inconsistencies and fix them in the working project, with bounded ownership of edits. Recheck affected behavior. If delegation is unavailable, perform the same audit and state that review was not independent. Avoid claiming perfection, clinical validation, or successful live rendering without evidence.

## 5. Deliver

Use `scripts/build_site.py --project <project> --output <new-output-directory>` to create an offline HTML and a buildless deployment folder/ZIP after adaptation. The build helper preserves complete geometry and splits compressed data into small files; it is not an anatomy generator or validation substitute. Check the source provenance, atlas licenses, output consistency and ZIP integrity. Reuse `assets/source/atlas-tools` only when relevant to the chosen dataset.

Deliver a complete editable static site with root `index.html`, all runtime/anatomy assets and a source ZIP ready for GitHub Pages or Netlify. Include a local HTTP preview and VS Code instructions. Include the build helper’s standalone offline guide and summarize verification and known limitations. Include separate 3D model exports if requested; interactive website configurations must work even without external GLB downloads. Keep working data and developer notes out of the public interface. Do not publish merely because the template was invoked: deployment follows the user's requested destination and authorization.

## Study text, paper figures and skin marking

Keep the short step summary visible. Follow it with one compact **Details** dropdown and one paragraph that explains the anatomy, purpose and relationships at a medical student level. Use the first step to introduce the approach. Put short citation markers at the end of each paragraph, list the full linked citations explicitly inside that step’s Details disclosure, and keep the complete bibliography in Papers. Use an atlas chapter when available. Identify model-only reversals and reconstruction choices.

Bundle a verified source image for every step and variant in **2D Figures**. For a paper-specific case, use figures from that paper. When there is no direct illustration, reuse the closest related figure and label it as context. Record the figure and panel, citation, publisher link, source page and license. Check redistribution rights for the intended audience. Render the images as soon as readers open the tab.

Add a high-contrast, borderless **Back** link to the left of the title for every simulation reached from a library. Return to the library page that launched the guide. Use the Procedure Library or Operative Cases index as the direct-entry fallback for the respective guide.

Draw black skin ink in the skin mesh’s rest coordinates at the marking step. Keep it visible on the exterior skin through later steps, moving with both cut edges and any reflected flaps. Keep other teaching overlays distinct. Clear and hide the anatomy labels and their leader SVG while 2D Figures is active.

## Clinical overview and expanded reading

Every completed procedure guide and operative case includes an **Overview** tab with approximately one substantive page of source-supported teaching material. Adapt it to the specific procedure or article: explain relevant anatomy, indications and selection, preoperative assessment, goals, outcomes, complications and evidence limitations. For article-specific cases distinguish the reported case and study findings from general background, and do not invent clinical outcome rates. Cite claims with linked sources. Write for a second-year medical student using clear, precise clinical prose: explain anatomical relationships and the reasoning behind clinical choices without oversimplifying, using first-person opinions, conversational prompts, or imitating a source's prose. Preserve meaningful depth rather than a brief patient-facing summary.

Keep the standard visual-first layout. Provide the small accessible control at the boundary beside the reading panel to expand it to about 60% of the desktop width, shrink the model to the remaining 40%, and restore the original layout on a second activation. Let overview text use the available panel width. On mobile, expand the reading area vertically and keep the controls accessible without overlap. Switching tabs or expanding the reader must preserve the active step and camera. Use the retained reference implementation as the starting point, not a visual approximation.

## Video sources, 2D frames and step synchronization

When an article has an accompanying operative video, especially when an operative case is based on that one article, locate and watch the entire accessible video from beginning to end. An article URL is sufficient to start: follow its video link, use available authorized access, and read the complete article. Record the video duration, source, time ranges and observed actions; map the footage to the article and the case-specific sequence. A transcript or abstract helps navigation but does not replace watching the complete video. Never claim to have watched an inaccessible segment. If access or playback fails, explain exactly what was reviewed and request an accessible link or video file; do not bypass access restrictions.

Extract clear, directly relevant frames at verified timestamps for the 2D Figures view. Use enough frames to show distinct fine steps or meaningful transitions, not a single image for an entire exposure. Map each image to the appropriate step, record its timestamp and observed action, and credit the video title, authors, source link and applicable license. For a single-article operative case, prioritize the accompanying video and the paper's own figures. If a step is not actually shown, label it as not shown and use an appropriately labeled related figure when available; never fabricate a timestamp or present unrelated footage as the action. Check the intended use and applicable reuse rights before bundling frames or publishing; access alone does not establish redistribution rights.

When the user supplies a playable video file, include an accessible collapsed **Operative Video** disclosure above the Guide / Indications / Papers tabs within the content panel. Expanding it reveals an embedded player and pushes the tabs and their content below it in normal document flow; collapsing it reclaims the space. Support desktop and mobile without overlapping or clipping the model, controls, tabs or step content. Show the video source and credit, provide native playback controls, and do not autoplay. Preserve the guide's selected step, camera and other state when toggling the disclosure.

Associate each step with a verified timestamp in the supplied video when that action is actually shown. On any step selection or Previous/Next navigation, seek the player to that step's timestamp, including when the disclosure is collapsed; synchronize the initial step once metadata is ready. Keep playback paused if it was paused and preserve playing state if already playing; never start playback merely because a step changes. If metadata is not yet available, queue only the latest requested seek and apply it after loading. If an action is not shown or its timestamp cannot be verified, mark the step as unavailable in the video and do not seek to a fabricated or unrelated timestamp. Handle a missing, unsupported or failed video with a clear message and leave the guide usable. Preserve the mapping and media in the delivered site where the user has supplied the file and the intended distribution is authorized; never silently publish a supplied or copyrighted video without confirming applicable rights.

Verify the full-video review and source-to-step time map, inspect extracted frames, test the disclosure and video controls on desktop and mobile, and check initial, forward, backward, direct step selection and rapid navigation both open and collapsed. Verify timing within a reasonable seek tolerance, state preservation, unavailable timestamps, metadata delays, failed media and keyboard access. Report access, reuse and unverified timestamp limitations honestly. When the user excludes operative case pages from a particular bulk edit, honor that scope for that task.
